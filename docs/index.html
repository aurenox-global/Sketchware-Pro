#What is Sketchware Pro?

Sketchware was an app that let you build Android apps visually, with blocks, right on your phone. Development stopped years ago. Sketchware Pro is a community mod that keeps it alive, fixes what was broken and adds what the original never had.

🧩

Blocks, but real code

Design with visual blocks and Sketchware Pro generates genuine Java. Nothing is locked in a proprietary format: you can read, edit and export the code.

📱

A full IDE on Android

Layout editor, logic editor, resources, libraries, manifest, signing and compilation — all running on the device itself.

🧱

Project catalogue

Start from a template, a blank project or a shared .swb file. Everything lives in your storage and stays yours.

🔓

Community-driven

Made by the community for the community. Free, with no subscription and no telemetry of its own.

Important: this project is a mod of Sketchware. It is source-available, not open source, and it is not allowed on Google Play or any other app store. Install it by sideloading only. See the legal notice.

#Main features

What you actually get inside the app.

Visual layout editor

Drag widgets onto a canvas, edit properties, preview and generate the XML.

Logic / blocks editor

Events, conditions, loops, variables and functions — with a searchable block palette.

Code editor

Syntax highlighting, autocomplete and a file tree for the generated sources.

Java & Kotlin

Kotlin compilation is supported through the bundled kotlinc toolchain.

Library manager

Firebase, Material Components, Glide, Retrofit and many more, ready to add to your project.

On-device compiler

Builds the APK on the phone, with a bundled aapt2 per architecture.

Resource editor

Images, colors, fonts, sounds and strings without leaving the app.

Custom blocks

Create your own blocks and share them with the community.

Built-in debugger

Logcat, error reports and, in recent versions, real debugging work in progress.

2026-09-24 · build & signing

Sign with your keystore, and compile APK or AAB from one dialog highlight fixed

  • The IDE now signs with your own keystore, and compiling is one dialog: APK or AAB × saved keystore / keystore file / testkey / don't sign. Where it started, measured and not guessed: the Sign an APK file tool in Settings never looked at your keystore — both of its calls hard-coded useTestkey=true, so it always signed with the AOSP testkey (apksigner verify → a40da80a…, not your certificate). The sign dialog assumed a fixed path (/storage/emulated/0/sketchware/keystore/release_key.jks) and had a single password field, so the same password had to be both the store and the alias password, and the APK branch of ExportProjectActivity ignored the dialog path and reused the alias password as the store password — a real .jks (the normal keytool case, two different passwords) was simply unusable.
  • New keystore manager (Settings → General): imports .jks / .keystore / .bks / .p12 after validating the credentials, copies the file into private app storage (filesDir/keystores/, not /sdcard, which anyone can read), stores alias + store and key passwords encrypted and shows each certificate — the SHA-256 it displays is identical to keytool (B1:46:48:5F:…:C4). The shared sign dialog now has an explicit keystore path, store password separate from the alias password, a saved-keystore picker that fills everything in, and it no longer closes on a validation error (it used to lose what you had typed). It reads that JKS with a type-agnostic loader, because on Android KeyStore.getInstance("JKS") resolves to BKS and a real JKS cannot be opened. And Settings → Sign an APK file finally asks which key to use (testkey or each saved keystore) and shows the resulting certificate, instead of signing silently with a key you did not choose.
  • The on-device build was blocking all of it, and those were real bugs of the IDE, not the test projects. DexMerger (the fork's dx) died with java.nio.BufferOverflowException on any release/AAB build — the library dexes the IDE injects share a single debug_info_item among up to 116 methods while the merger wrote a fresh copy per code_item and reserved space with the already deduplicated byte count; fixed by deduplicating on (input dex, offset): debug info items 2,297 → 361 (reproduced offline with the two real dexes, same stack as the device). Export AAB was broken by R8 — protobuf resolves the generated getters by reflection, so getBundletool was gone from the release dex (0 → 7 occurrences after the -keep). The release APK was V1-only and would not install on Android 11+ (INSTALL_PARSE_FAILED_NO_CERTIFICATES), now apksig V1+V2+V3; and the AAB carried SHA-1 digests (jarsigner treated it as unsigned) → SHA-256, jar verified.
  • Two more build-killers fixed on the way. A resource XML written with only the header (NONE.xml, straight out of the "Create a new file" dialog) made aapt2 fail the whole build (no element found) → valid per-folder templates, name validation and a guard that moves root-less XML to .invalid-xml-skipped/ with a warning (recoverable, nothing is deleted). And R8 deleted the <init> of its own embedded R8/D8 threading providers, which that same R8 instantiates by reflection (the class name survives in a string, so the failure was NoSuchMethodException and deterministic): "Failure creating provider for the threading module" → -keep class com.android.tools.r8.threading.** { *; } (+1,196 B, ~0.001 % of the APK), proven before/after on the device with a probe that replays that exact factory.
  • Verified in the release APK (R8): an APK release signed with your certificate (apksigner verify: Verifies, V1+V2+V3, b146485f…) and installed from the dialog's own Install button (the system installer offered to update the app); an AAB with the full bundle structure (BundleConfig.pb, base/manifest, base/dex, base/res/*, base/resources.pb) and jarsigner -verify → jar verified; Run ▶ untouched (debug, testkey a40da80a…); the unsigned mode writes .unsigned. Five UI bugs found while measuring were fixed too — the format spinner was invisible, the signing label lied, NEXT fell off the screen, Install crashed the app (FileProvider didn't expose sketchware/signed_apk/) and it offered to install an unsigned APK.

Honest: the AAB has not been checked against bundletool or Play (there is no bundletool on this machine), the keystore file and testkey modes of the dialog were not executed for release (UI only), and converting Android Studio/GitHub projects is still pending (next round: viability + MVP). 2026-09-24 · preview

The colours you pick are no longer written transparent into the XML highlight fixed

  • The colours you pick in the editor came out transparent — in the preview and in the compiled app. A bug inherited from the original Sketchware Pro, and deterministic, not a rare case: any background colour chosen from the hexadecimal palette was written to the XML as #00RRGGBB — alpha 00, fully transparent — so the view was drawn with no colour at all and the app said nothing ("Preview OK"). Reproduced in the real flow (editor → Ox → preview), not only by injecting XML: with button1 = #2196F3 and linear1 = #4CAF50 the real preview showed 0 blue px and 0 green px, and the same XML injected reproduced it identically; with the alpha corrected it went to 30,524 / 593,519 px.
  • Root cause, one line. a/a/a/Ox.java did int color = backgroundColor & 0xffffff before formatting, and formatColor prints 8 digits whenever the alpha is not 0xFF — so 0xFF2196F3 became 0x002196F3 → "#002196F3". The same mask also hit backgroundTint, cardBackgroundColor and contentScrim, and the text paths (textColor, textColorHint).
  • The fix: stop masking the alpha at those 4 places (Ox.java:201, 418, 824, 847; formatColor itself was not touched). Measured in the release APK (R8) with the real flow: blue 0 → 30,398 px, green 0 → 333,317 px, red text 0 → 577 px. The XML now carries #2196F3 / #4CAF50 / #F44336 (6 digits), and the translucent #802196F3 keeps its alpha (8 digits, 0x80 intact, which the old mask would have zeroed). The layout the IDE compiles (mysc/601/…/res/layout/main.xml) carries the right colours too. Regression exact: r8 caseA/caseC and r11 caseE pixel-identical (356,400 px, same bounding box). Honest: the IDE's own aapt2 link step still fails later on for a preexisting AppCompat resource problem of that project, unrelated to these 4 lines.

#Install

There is no store version. You install the APK yourself.

  1. Download the right APK from the releases page: app-arm64-v8a-release.apk for almost every modern phone, app-armeabi-v7a-release.apk for old 32-bit devices, x86_64/x86 for emulators.
  2. Allow installation from unknown sources for your browser or file manager (Android will ask you when you open the file).
  3. Open the APK and install. The signing key is unchanged, so it installs over previous builds.
  4. Optional: install over ADB, which also keeps your data.
adb install -r app-arm64-v8a-release.apk
Requirements: Android 8.0 (API 26) or newer. An ARM64 device is recommended — the bundled compiler and toolchain work best there.

#Build it yourself

From source to APK. Takes a while the first time, then it is quick.

  • JDK 17 — java -version should report 17.x.
  • Android SDK — platform 36 and build-tools 35 installed; point local.properties at it (sdk.dir=/path/to/android-sdk).
  • Google Services file — app/google-services.json is optional; the build scripts create a temporary placeholder from app/src/debug/google-services.json if needed.
# debug build
./gradlew :app:assembleDebug

# release build (signed)
./gradlew :app:assembleRelease

# or use the helper scripts
./compile_project.command
./compile_release.command
Signing warning. If RELEASE_STORE_FILE, RELEASE_STORE_PASSWORD, RELEASE_KEY_ALIAS and RELEASE_KEY_PASSWORD are not set, the build falls back to the repository's bundled testkey.keystore — a public AOSP test key. The resulting APK is fine for local testing, but anyone could sign an update that Android would accept as yours. Never publish an APK signed with it.

#FAQ

Is it free?

Yes. No subscription, no ads, no payment of any kind. The upstream project accepts support through Patreon only to keep development going.

Can I publish it on Google Play?

No. Sketchware Pro is a mod of Sketchware and publishing it — original or modified — on any app store is explicitly not allowed.

Does it need a computer?

No. The whole IDE and the compiler run on the phone. A computer is only useful for building this repository from source.

Are the apps I make mine?

Yes. Sketchware Pro generates plain Android sources and resources, and the APKs you build belong to you. What is not yours is Sketchware Pro's own code.

Why is the APK so large?

It bundles the on-device compiler, four aapt2 binaries, an Android jar, library archives and a Kotlin toolchain. ABI splits already cut it from 141 MB to about 129 MB per device; code and resource shrinking are still on the roadmap.

Why does the release use a test key?

On purpose: it is the original signing identity, so updates install over existing builds. It is a public key, so treat these APKs as sideload/testing builds and switch to the private keystore only if you accept a full reinstall.
