#What is Sketchware Pro?

Sketchware was an app that let you build Android apps visually, with blocks, right on your phone. Development stopped years ago. Sketchware Pro is a community mod that keeps it alive, fixes what was broken and adds what the original never had.

🧩

Blocks, but real code

Design with visual blocks and Sketchware Pro generates genuine Java. Nothing is locked in a proprietary format: you can read, edit and export the code.

📱

A full IDE on Android

Layout editor, logic editor, resources, libraries, manifest, signing and compilation — all running on the device itself.

🧱

Project catalogue

Start from a template, a blank project or a shared .swb file. Everything lives in your storage and stays yours.

🔓

Community-driven

Made by the community for the community. Free, with no subscription and no telemetry of its own.

Important: this project is a mod of Sketchware. It is source-available, not open source, and it is not allowed on Google Play or any other app store. Install it by sideloading only. See the legal notice.

#Main features

What you actually get inside the app.

Visual layout editor

Drag widgets onto a canvas, edit properties, preview and generate the XML.

Logic / blocks editor

Events, conditions, loops, variables and functions — with a searchable block palette.

Code editor

Syntax highlighting, autocomplete and a file tree for the generated sources.

Java & Kotlin

Kotlin compilation is supported through the bundled kotlinc toolchain.

Library manager

Firebase, Material Components, Glide, Retrofit and many more, ready to add to your project.

On-device compiler

Builds the APK on the phone, with a bundled aapt2 per architecture.

Resource editor

Images, colors, fonts, sounds and strings without leaving the app.

Custom blocks

Create your own blocks and share them with the community.

Built-in debugger

Logcat, error reports and, in recent versions, real debugging work in progress.

2026-09-24 · Flutter + preview

The toolchain no longer says "not installed", and the inherited icon names highlight fixed

  • The "not installed" was our check, not your install. The installer verified the Dart SDK by running <filesDir>/flutter-toolchain/dart/bin/dart --version, and SELinux forbids executing an ELF that lives in the app's data directory (execute_no_trans, error=13, untrusted_app). The probe returned null, the install aborted before downloading the engine artifacts and the UI ended at Toolchain de Flutter no instalado after 91 MB — a bug in our check, with the SDK data already on disk.
  • "Installed" is now a data criterion. The marker installed.properties, the AOT snapshots gen_kernel_aot.dart.snapshot and dartdev_aot.dart.snapshot and lib/_internal/vm_platform.dill decide it; a bin/dart that will not start can no longer turn a correct extraction into "not installed". "Can compile" adds a real execution probe launched from the native libraries directory (nativeLibraryDir/libdartaotruntime.so), so bin/dart is never executed again and every message names the piece, the path and the cause, plus an honest intermediate state (SDK Dart … extraido … pero NO listo para compilar) instead of blaming W^X.
  • A second, pre-existing bug fixed. The pub dependencies were extracted with a <package>-<version>/ prefix that pub.dev tarballs do not carry, so 0 files were written and the install died with El paquete characters 1.4.1 no se extrajo bien; it now retries without the prefix. The consent dialog also warns about the real disk space: the download is ~307 MB, but extracted the toolchain takes ~800 MB.
  • Verified on an arm64 API 34 emulator: the full install ends at Toolchain Flutter: instalado (Dart 3.13.4) · 813.7 MB and the installer log shows the app running nativeLibraryDir/lib/arm64/libdartaotruntime.so inside its own process. Honest: the full compile (pub get + build) inside the app could not be automated on the emulator and is not claimed; what is proven is that the packaged binary does run in the app's process.
  • Inherited icon names. ic_tune_white exists in no source of this IDE — 2,382 drawables were dumped and the current equivalent is ic_tune_24/ic_mtrl_tune — so the preview now resolves those old names as a last resort, only after project, assets, libraries and the IDE, normalising prefixes (ic_, img_, icon_) and colour/size suffixes; a single match is used, several are called ambiguous and stay red. And nothing happens silently: its own group in the detail dialog (Nombre heredado resuelto -> @drawable/ic_tune_white -> @drawable/ic_tune_24), an amber info bar when there is no real failure, and the log.
  • Measured: the real case goes from 2 red blocks (2,080 px) to 1 (1,040 px) and the bar reads 1 recurso no encontrado · 1 nombre heredado resuelto; the round-4 grouped detail and every earlier preview case keep working. Honest pending: it covers the names whose concept still exists (~19/44 of the families tested); typos, mipmaps and concepts with no current icon stay red.

2026-09-23 · fix

Design preview paints again highlight fixed

  • The symptom. The preview of View-based designs (the HTML/WebView preview always worked) showed the design area empty — white or black depending on the theme — with only the widgets that paint themselves (SeekBar, Switch, icons) and the WebView HTML visible.
  • The cause was a sentinel. The IDE's own data model stores 0xffffff for "no colour chosen" (TextBean.textColor/hintColor, LayoutBean.backgroundColor), and LayoutPreviewActivity applied it as a real colour: as an int, 0xffffff is 0x00FFFFFF — alpha 0 — so the text became fully transparent and the background the widget's own theme would have painted was wiped instead. ViewPane made it worse by forcing a white canvas in preview mode while the views were inflated with the IDE theme, which is why the contrast flipped with the theme.
  • The fix. 0xffffff (and any zero-alpha colour) now means "not set" and the theme decides; the preview canvas uses the colorSurface of the same theme that inflates the views; the inflated root keeps the dimensions declared in the XML; and a view the IDE cannot instantiate shows a red marker plus a "partial preview" notice instead of a silent gap.
  • Verified on an arm64 API 34 emulator: the same layout, light and dark, now paints the button — its area measured 255,255,255 with zero glyphs before — and HTML/WebView previews keep working (Preview OK · vistas: 3 · WebViews: 1).
  • Honest pending: Material components (MaterialButton, CardView), Material3 projects and custom project themes are not verified on screen, and nothing has been tested on a physical phone.

2026-09-23 · Flutter (experimental)

Release/AOT on the device, complete assets and real pub highlight experimental

  • Release/AOT is unlocked on the device. The Dart SDK for Android was built for this fork with compressed pointers — the flag comes from the architecture name (arm64c), not from a command-line option — and as a product build, because the first token of the snapshot's feature string is decided at compile time (product, not release). Its gen_snapshot (4,991,592 B, sha256 9921983f…) ships inside the APK and with it the phone itself produces a libapp.so the official engine accepts. Tested: a release APK boots in an arm64 Android 14 emulator, the counter goes 0 → 3 on real taps and there is no DEBUG banner. Control A/B: the same APK with the Termux SDK's gen_snapshot fails with the snapshot requires 'no-compressed-pointers' but the VM has 'compressed-pointers' — only compressed pointers were missing.
  • The app can run its own tools. With targetSdk 34, SELinux denies execute_no_trans for binaries in filesDir and in /data/local/tmp, but nativeLibraryDir works: the runtime and gen_snapshot are packed as lib/arm64-v8a/libdartaotruntime.so and libfluttergensnapshot.so. The app ran the whole AOT from its own process, as an untrusted app and without root, in 3.9 s and with the same sha256.
  • The asset bundle is complete. Material Icons (the real pin is bin/internal/material_fonts.version → fonts.zip, not an engine artifact), the ink_sparkle.frag and stretch_effect.frag shaders precompiled on the host and embedded, AssetManifest.bin (StandardMessageCodec), FontManifest.json and NOTICES.Z. Verified on the device: the + icon is drawn and the shader error is gone.
  • Real pub. dart pub get now runs on the device (the pub client ships in the Dart SDK itself) and resolves real pub.dev packages, and the kernel is compiled with the resulting authentic package_config.json.
  • Plugins: half-way, stated honestly. The fork has its own Kotlin/Java plugin compiler (ECJ plus the fork's K2JVMCompiler) that generates the GeneratedPluginRegistrant, merges manifests and pulls AAR dependencies; no plugin has been compiled or started on a device yet — that is the first pending item.
  • Cost and limits. The two packed executables add 10.18 MB to the arm64-v8a APK; other ABIs have no AOT backend and say so instead of failing silently. The default mode is still debug/JIT, this stays experimental and there is still no hot reload.

Version v7.0.8.0 (versionCode 162). The commands, the measured numbers and the honest pending work are documented in docs/flutter-fase8.md.

Flutter support: Dart editor and builds on the device highlight experimental

  • The editor understands Dart. .dart files get the TextMate Dart grammar (from the Dart-Code project, MIT), its language configuration, bracket matching and Dart completions, plus a Flutter icon in the menus.
  • A Flutter project type. 2026-09-21 · CI

CI is green done

The last blocker was subtle: the bundletool jar that GitHub Actions downloads ships embedded classes.dex files next to Java bytecode, and R8 refuses an archive with both — the local Gradle cache has the same version without them. #Install

There is no store version. You install the APK yourself.

  1. Download the right APK from the releases page: app-arm64-v8a-release.apk for almost every modern phone, app-armeabi-v7a-release.apk for old 32-bit devices, x86_64/x86 for emulators.
  2. Allow installation from unknown sources for your browser or file manager (Android will ask you when you open the file).
  3. Open the APK and install. The signing key is unchanged, so it installs over previous builds.
  4. Optional: install over ADB, which also keeps your data.
adb install -r app-arm64-v8a-release.apk
Requirements: Android 8.0 (API 26) or newer. An ARM64 device is recommended — the bundled compiler and toolchain work best there.

#Build it yourself

From source to APK. Takes a while the first time, then it is quick.

  • JDK 17 — java -version should report 17.x.
  • Android SDK — platform 36 and build-tools 35 installed; point local.properties at it (sdk.dir=/path/to/android-sdk).
  • Google Services file — app/google-services.json is optional; the build scripts create a temporary placeholder from app/src/debug/google-services.json if needed.
# debug build
./gradlew :app:assembleDebug

# release build (signed)
./gradlew :app:assembleRelease

# or use the helper scripts
./compile_project.command
./compile_release.command
Signing warning. If RELEASE_STORE_FILE, RELEASE_STORE_PASSWORD, RELEASE_KEY_ALIAS and RELEASE_KEY_PASSWORD are not set, the build falls back to the repository's bundled testkey.keystore — a public AOSP test key. The resulting APK is fine for local testing, but anyone could sign an update that Android would accept as yours. Never publish an APK signed with it.

#FAQ

Is it free?

Yes. No subscription, no ads, no payment of any kind. The upstream project accepts support through Patreon only to keep development going.

Can I publish it on Google Play?

No. Sketchware Pro is a mod of Sketchware and publishing it — original or modified — on any app store is explicitly not allowed.

Does it need a computer?

No. The whole IDE and the compiler run on the phone. A computer is only useful for building this repository from source.

Are the apps I make mine?

Yes. Sketchware Pro generates plain Android sources and resources, and the APKs you build belong to you. What is not yours is Sketchware Pro's own code.

Why is the APK so large?

It bundles the on-device compiler, four aapt2 binaries, an Android jar, library archives and a Kotlin toolchain. ABI splits already cut it from 141 MB to about 129 MB per device; code and resource shrinking are still on the roadmap.

Why does the release use a test key?

On purpose: it is the original signing identity, so updates install over existing builds. It is a public key, so treat these APKs as sideload/testing builds and switch to the private keystore only if you accept a full reinstall.
